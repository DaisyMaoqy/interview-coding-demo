# 校验规则清单

本文汇总系统中全部的校验规则及其设计动机。规则的实现分散在四个模块，
但**每条规则只有一处定义**，本文是它们的索引而非副本 —— 改规则请改代码，
本文随之更新。

| 层次             | 位置                                                   | 职责                                        |
| ---------------- | ------------------------------------------------------ | ------------------------------------------- |
| 输入归一化       | `src/lib/domain/money.ts`                              | 把用户敲进来的文本清洗成规范值              |
| 字段与跨字段校验 | `src/lib/domain/schemaConfig.ts`（由 `FieldDef` 推导） | 表单内容是否合法（原子 Zod 在 `schema.ts`） |
| 状态机校验       | `src/lib/domain/workflow.ts`                           | 这个人此刻能不能做这个动作                  |
| 导航校验         | `src/lib/domain/wizard.ts`                             | 用户能不能走到这一步                        |

---

## 一、输入归一化

`parseYuanInput()` 在数据进入 schema 之前先做清洗。归一化与校验分开，
是为了让 schema 只面对干净的数字，不必处理各种输入怪癖。

| 接受               | 示例            |
| ------------------ | --------------- |
| 千分位逗号         | `1,234.56`      |
| 货币符号           | `¥100`、`￥100` |
| 全角数字与全角句点 | `１２３．４５`  |
| 前后空白           | `  88.00  `     |
| 空串（视为未填写） | `''`            |

| 拒绝             | 原因                                                         |
| ---------------- | ------------------------------------------------------------ |
| 非数字文本       | ——                                                           |
| 科学计数法 `1e3` | `Number()` 解析过于宽松，会得到 1000，但用户不可能想输入这个 |
| 十六进制 `0x64`  | 同上，`Number('0x64')` = 100                                 |
| 超过两位小数     | 人民币最小单位是分                                           |

负号予以保留，**是否允许负数交给 schema 层判断** —— 解析函数只负责解析，不越权做业务判断。

### 金额一律以「分」存储

全链路使用整数分，仅在展示时转元。

```ts
yuanToCents(19.99); // 1999，而非浮点直乘得到的 1998.9999999999998
```

## 二、字段与跨字段校验

校验规则不再散落在各步骤组件，而是集中在 `src/lib/domain/applicationTypes.ts` 的
`FieldDef` 声明里，由 `src/lib/domain/schemaConfig.ts` 推导出逐步（`buildStepSchema`）
与整单（`buildTypeSchema`，含类型级 `typeRefine`）的 Zod schema。一套配置同时驱动
UI 渲染与校验，二者天然不漂移。当前 `travel`（差旅）与 `leave`（请假）字段不同，
下面按类型分述。

### 通用：实时校验交互

错误在后台始终计算，但只有「被用户交互过（touched）」或「点击过下一步/提交（attempted）」
的字段才展示；`touched` 在 `oninput` 与 `onblur` 都会标记，所以错误在**输入过程中**
就实时出现，不必等失焦。

### 差旅（travel）

**步骤 1 — 基本信息**

| 字段               | 规则                    | 提示文案                    |
| ------------------ | ----------------------- | --------------------------- |
| `reason` 出差事由  | trim 后 ≥ 10 字         | 出差事由请不少于 10 个字    |
|                    | ≤ 200 字                | 出差事由请控制在 200 字以内 |
| `urgency` 紧急程度 | 枚举 `normal \| urgent` | 请选择紧急程度              |

> **为什么事由要 10 字下限**：「出差」这类事由对审批人没有任何信息量，
> 审批人无法据此判断该不该批。

### 步骤 2 — 行程明细

**单字段**

| 字段                      | 规则                                   | 提示文案       |
| ------------------------- | -------------------------------------- | -------------- |
| `from` 出发地             | 非空                                   | 请填写出发地   |
|                           | ≤ 30 字                                | 地点名称过长   |
| `to` 目的地               | 非空                                   | 请填写目的地   |
|                           | ≤ 30 字                                | 地点名称过长   |
| `departDate` `returnDate` | 匹配 `YYYY-MM-DD`                      | 请选择日期     |
|                           | 日期真实存在                           | 日期不存在     |
| `transport` 交通方式      | 枚举 `train \| flight \| car \| other` | 请选择交通方式 |

> **为什么要单独校验日期存在性**：`2026-02-30` 能通过正则，
> 但 `new Date('2026-02-30')` 会静默滚到 3 月 2 日 —— 用户以为填的是 2 月，
> 系统存的是 3 月。所以格式校验之后还要回读确认。

**单段内的跨字段**

| 规则                       | 提示文案                 | 错误挂载字段 |
| -------------------------- | ------------------------ | ------------ |
| `returnDate >= departDate` | 返回日期不能早于出发日期 | `returnDate` |
| `from !== to`              | 出发地与目的地不能相同   | `to`         |

**段与段之间**

| 规则                     | 提示文案              |
| ------------------------ | --------------------- |
| 至少 1 段                | 请至少添加一段行程    |
| 最多 10 段（`MAX_LEGS`） | 最多添加 10 段行程    |
| 各段日期区间不重叠       | 与第 N 段行程日期重叠 |

> **重叠检测的实现**：先按出发日期排序再相邻比对，O(n log n)，而非两两比对的 O(n²)。
> 错误精确挂到冲突那一行的 `departDate`，UI 才能高亮具体某段，
> 而不是给一句笼统的「行程有冲突」让用户自己找。

### 步骤 3 — 费用预算

**单字段**

| 字段                                           | 规则                            | 提示文案                |
| ---------------------------------------------- | ------------------------------- | ----------------------- |
| `budget.transport` `hotel` `allowance` `other` | 整数（单位：分）                | 金额精确到分            |
|                                                | ≥ 0                             | 金额不能为负            |
|                                                | ≤ 1,000,000,000 分（1000 万元） | 金额超出合理范围        |
| `budgetNote` 说明                              | ≤ 200 字                        | 说明请控制在 200 字以内 |

**对象级**

| 规则                                 | 提示文案                       |
| ------------------------------------ | ------------------------------ |
| 四项合计 > 0                         | 预算合计需大于 0               |
| 合计 > 10,000 元时 `budgetNote` 必填 | 预算超过 10,000 元，请填写说明 |

> **超限不拒绝，只要求解释**：大额差旅是合理存在的业务场景，
> 系统需要的是一份说明供审批人参考，而不是把人挡在门外。
>
> 上限 1000 万元防的是误输一长串数字，不是业务约束。

> **`checkBudgetTotal` 为什么提成具名函数**：这条对象级规则同时被
> 第三步 schema 和整单 schema 引用。复制一份就意味着改阈值时必然漏掉其中一处。

### 请假（leave）

**步骤 1 — 基本信息**

| 字段                 | 规则                              | 提示文案                    |
| -------------------- | --------------------------------- | --------------------------- |
| `reason` 请假事由    | trim 后 ≥ 5 字                    | 请假事由请不少于 5 个字     |
|                      | ≤ 200 字                          | 请假事由请控制在 200 字以内 |
| `leaveType` 请假类型 | 枚举 `annual \| sick \| personal` | 请选择请假类型              |

**步骤 2 — 请假时间**

| 字段                          | 规则                                    | 提示文案                 |
| ----------------------------- | --------------------------------------- | ------------------------ |
| `leaveRange` 请假时间（区间） | 起止两端都必填；任一为空 → `请选择日期` | 请选择日期               |
|                               | 结束日期不早于开始日期                  | 结束日期不能早于开始日期 |
| `note` 备注                   | ≤ 200 字                                | 备注请控制在 200 字以内  |

> `leaveRange` 的值写在 `fromKey` / `toKey`（`leaveStart` / `leaveEnd`）上，而非 `field.key`；
> 跨字段 refine 在两端都填后校验 `end >= start`，空值由 `dateStringSchema` 的「请选择日期」统一兜住。

## 三、状态机校验

```html
draft ──submit──▶ pending_manager ──approve──▶ pending_finance ──approve──▶ approved │ │
├──reject──▶ rejected ◀─reject─┤ └──cancel──▶ cancelled ◀─cancel┘ rejected ──reedit──▶ draft
```

每次流转依次通过四道关卡，任一不过即返回失败：

| 关卡       | 失败码             | 校验内容                            |
| ---------- | ------------------ | ----------------------------------- |
| 状态合法性 | `invalid_status`   | 当前状态是否存在该动作的出边        |
| 操作人资格 | `forbidden`        | 见下表                              |
| 必填意见   | `comment_required` | 驳回时必须填写意见                  |
| 意见长度   | `comment_too_long` | 必填报销意见时，意见不得超过 200 字 |

**操作人资格**

| 动作                                 | 谁能执行                                  |
| ------------------------------------ | ----------------------------------------- |
| `submit` `cancel` `reedit`           | 仅申请人本人                              |
| `approve`(待主管审批) `reject`(主管) | `role === 'manager'` **且不是申请人本人** |
| `approve`(待财务审批) `reject`(财务) | `role === 'finance'` **且不是申请人本人** |

**其他约束**

| 规则                                                 | 动机                                                     |
| ---------------------------------------------------- | -------------------------------------------------------- |
| 已通过的单不可撤销（`approved` 无 `cancel` 出边）    | 差旅已成行，撤销没有业务含义                             |
| 驳回必须填写意见                                     | 否则申请人不知道该改什么                                 |
| 驳回意见不超过 200 字（`REJECT_COMMENT_MAX_LENGTH`） | 避免意见无限拉长，`transition` 直接拒绝                  |
| 只有本人的草稿可编辑、可删除                         | `isEditable` / `isDeletable`                             |
| 每次提交都刷新 `submittedAt`                         | 重新编辑后再提交应以最新提交时间为准；时间按本地时区存储 |

**查看权限（`canViewRequest`）**

流转权限判断「这个人此刻能不能做这个动作」，查看权限判断「这张单这个人看不看得到」，
两者正交 —— 能看不代表能审批，审批仍受上面「不能自审」等流转表约束。详情页据此渲染
「无权查看」分支，随身份切换响应式变化。

| 场景                                        | 结果                             |
| ------------------------------------------- | -------------------------------- |
| 自己的单（任意状态）                        | 可看                             |
| 经理看员工的**非草稿**单（含已审批/已驳回） | 可看（便于主管掌握团队申请进展） |
| 财务看**待财务审批**的单                    | 可看（财务的二审队列）           |
| 员工看他人或领导的单                        | 不可看                           |
| 经理看员工的草稿                            | 不可看（草稿仅申请人自己可见）   |
| 经理看其他经理的单                          | 不可看                           |
| 财务看非待财务审批的单                      | 不可看                           |

> **不抛异常**：`transition()` 返回判别联合 `TransitionResult`。
> 非法流转是可预期的业务结果（例如两个标签页同时操作同一张单），
> 不是程序缺陷 —— 调用方应当展示提示，而不是让页面崩溃。

> **不能自审**是实践中最容易撞上的越权，单独给了一句更具体的提示
> 「不能审批自己提交的申请」，而不是笼统的「你没有权限」。

> **声明式流转表**：谁能在什么状态下做什么，集中在 `TRANSITIONS` 一张表里。
> 未来加一个审批环节只需改表，不必去各个页面里翻 `if`。

## 四、导航校验

| 规则                          | 说明                                      |
| ----------------------------- | ----------------------------------------- |
| `isWizardSlug()` 路由参数守卫 | 把任意字符串收窄成合法 slug，非法值走 404 |
| 步骤可达性                    | 已完成的步骤 + 第一个未完成的步骤可点     |

> **为什么不允许跳到更靠后的步骤**：用户会在预算页看到空行程，
> 而跨字段规则（如日期重叠）在缺少前序数据时根本无从校验。

## 五、校验规则的复用

同一份推导出的 schema 在两处被调用，规则只定义一次，不会漂移：

| 调用方                    | 作用                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 客户端向导 `StepRenderer` | 「下一步 / 提交」时 `validate(schema, draft)` 一次性校验，错误按字段路径展示，配合 `touched` / `attempted` 实时提示 |
| localStorage 草稿回读     | 结构变更或被手改过的脏数据一律丢弃                                                                                  |

字段类型由 `FieldDef` 驱动、Zod schema 由 `schemaConfig` 推导，改配置时校验自动跟随，不会各自为政。

### 错误结构

`toFieldErrors()` 把 `ZodError` 拍平成点号路径：

```ts
{ 'legs.0.returnDate': '返回日期不能早于出发日期' }
```

用扁平的字符串键而非 zod 原生的嵌套结构，表单组件可以直接查到自己的错误，
不必层层解构。同一字段只保留第一条消息，避免 UI 上堆叠多行提示。
